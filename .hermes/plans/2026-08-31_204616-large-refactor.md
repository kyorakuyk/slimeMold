# SlimeMold 大规模重构实施计划

> **For Hermes:** 先按本计划逐项审查和实现；在用户确认设计前，不创建 checkpoint commit，也不删除旧实现。

**Goal:** 将 SlimeMold 重构为一个由统一领域状态驱动的、本地优先的项目控制与执行系统：默认入口帮助用户把鬼点子收敛成经确认的计划，专业用户通过版本化扩展点获得足够的 Agent、Workflow、Runtime 和 UI 自定义能力。

**Architecture:** 采用“事件为事实来源、Materialized State/Snapshot 为查询与恢复缓存、Command 负责状态迁移校验、Projection 负责 UI”的架构。A 项目驾驶舱是默认入口，C Agent Lab 是全局配置与试验入口，DAG/Workflow 是项目上下文中的专业执行与检查视图。宿主保留状态、权限、证据、身份/迁移和副作用审批不变量；Provider、Node、Tool、Routing、Memory 和 Projection 通过版本化扩展点开放。

**Tech Stack:** React + TypeScript + Zustand + React Flow + Tauri 2 + Rust + Codex CLI/API/Ollama adapters + `.slimemold` directory persistence.

---

## 0. 已确认的产品决策

- 默认入口：A 项目驾驶舱；C 通用 LLM 工作台作为全局 Agent Lab / 高级设置。
- 初学者：看到叙事化阶段、决策、任务进度和 Evidence；实际 DAG 可以展开查看。
- 专业用户：可扩展 Provider、Agent、Role、Prompt、路由、预算、节点、DAG、Runtime policy、沙箱、权限、事件和恢复策略，但不能覆盖宿主不变量。
- 自动执行：用户确认计划后，可以自动执行任务、测试、采集证据，并按已确认的项目策略自动 push；管理类 Agent 可以在被授予的边界内确认 merge，但用户可以随时禁止 Agent 代为决断。发布、破坏性清理和 protected branch 操作仍受更高等级边界约束。
- 失败语义：独立任务失败后继续执行不依赖它的任务；依赖任务变为 `blocked`，失败回流为 Issue。
- 运行目标：项目设置 `cost-first / quality-first / speed-first / balanced`，每次 Run 可以临时覆盖。
- 记忆：项目记忆为主；安全白名单中的用户偏好/脱敏环境事实可以自动提升，其它全局记忆候选在项目结束时由用户确认。
- 旧数据：保留旧 `.slimemold`，允许一次性、可回滚的 schema 迁移。
- 第一条闭环：目标 → 主控澄清 → Brief/计划批准 → 隔离 worktree 中的一条真实 Codex Worker 任务 → 宿主测试/Evidence，并满足持久化、来源/批准、审批门、执行草案、跨页面一致性和一次真实 Codex/Agent 调用 6 项验收。

## 2. 宿主不变量

以下内容由 SlimeMold 宿主强制保护，插件和 Agent 不能覆盖：

1. **状态不变量**
   - 状态只能通过经过校验的 Command 迁移；
   - `aggregateVersion` 和事件顺序不能回退；
   - 未批准对象不能进入已批准/执行状态；
   - 依赖未满足的 Task 不能被标记为可执行。

2. **权限不变量**
   - 文件路径必须经过 canonicalize 和 workspace scope 校验；
   - 进程、网络、凭据、worktree、protected branch 和发布权限 fail-closed；
   - 插件只能获得 capability manifest 声明的权限；
   - 记忆永远不能替代当前上下文的副作用授权。

3. **证据不变量**
   - 测试、命令退出码、diff、策略检查、哈希和时间由宿主采集；
   - Agent 自报“完成”不能直接生成成功 Evidence；
   - Evidence 一旦作为验收事实写入，只能追加修订或标记失效，不能静默覆盖。

4. **身份、来源和迁移不变量**
   - 所有 Session、Decision、Issue、Artifact、Task、Workflow、Run、Evidence 有稳定 ID；
   - 派生对象保存来源 ID、来源版本、生成者、批准者和有效性；
   - 迁移先备份、可重放、可验证、失败可回滚；
   - 未识别的旧字段不能被静默丢弃。

5. **副作用和预算不变量**
   - push、merge、release、delete、生产修改等高影响操作必须有当前项目策略和运行时边界；自动 push 可以由已确认的项目策略持续允许，但不能扩大到 protected branch/force push/release；
   - 全局偏好本身只提供默认值；用户一次明确接受后，可以生成受边界约束的 ProjectExecutionPolicy，之后不因每个 Run 重复打断；
   - 重试次数、退避、预算消耗和停止/取消必须有上限；
   - 每个副作用都要有可追溯的 Command、actor、Policy 和 Evidence。

## 3. 第一版扩展点

### 3.1 Provider / Transport / Auth Adapter

```ts
interface ProviderAdapter {
  id: string;
  version: string;
  capabilities: {
    chat: boolean;
    streaming: boolean;
    toolCall: boolean;
    structuredOutput: boolean;
    subscriptionAuth: boolean;
  };
  auth: AuthAdapter;
  chat(request: ProviderChatRequest): Promise<ProviderChatResult>;
}
```

覆盖范围：OpenAI API、Anthropic API、Ollama、ChatGPT 计划版 Codex CLI。凭据由宿主管理；Adapter 不可直接读取项目文件、任意环境变量或其它 Provider 的凭据。

### 3.2 Agent / Role / Prompt Profile

允许专业用户创建 Agent、Role、系统提示词、上下文策略、模型和温度配置。Profile 只能产生 Provider request 或 Command proposal，不能直接写 Project State。

### 3.3 Task / Node / Workflow Extension

允许插件注册有 schema、版本和 capability manifest 的 Node/Task/Workflow 类型。插件执行结果必须经过宿主校验并转成 Domain Event；插件不能直接调用 Zustand store 或写 `.slimemold` 核心文件。

### 3.4 Routing / Objective / Retry Policy

允许自定义 cost/quality/speed 权重、Agent fallback、任务并发和有限重试策略。Policy 只能在宿主提供的候选范围内选择，不能放宽权限、批准自己或修改 Evidence。

### 3.5 Memory / Evaluation / Projection

允许自定义经验提取器、用户反馈评分器、报表和 UI Projection。Memory extractor 只能生成 `MemoryCandidate`；全局提升、策略生效和状态变更仍由宿主 Command 与用户确认控制。Projection 只能读 canonical state，不能建立独立真相。

## 4. 目标事件契约

目标文件：`.slimemold/events/events.jsonl`。每个项目一个追加事件流；应用级全局设置、全局 Agent 和全局记忆保存在 AppData 的独立应用存储中。

```ts
interface DomainEvent<TPayload = unknown> {
  eventId: string;
  streamId: string;                 // projectId
  sequence: number;                // 项目流内严格递增
  aggregateType: 'Project' | 'Session' | 'Decision' | 'Issue' | 'Artifact' | 'TaskGraph' | 'Task' | 'Workflow' | 'Run' | 'Evidence' | 'Memory';
  aggregateId: string;
  aggregateVersion: number;
  eventType: string;
  schemaVersion: number;
  payload: TPayload;
  actor: 'user' | 'master' | 'runtime' | 'system' | `plugin:${string}`;
  occurredAt: string;
  causationId?: string;
  correlationId?: string;
  source?: {
    objectId: string;
    objectVersion: number;
  };
  sensitivity: 'normal' | 'private';
}
```

禁止在事件 payload 中存放 API Key、OAuth token、Cookie、完整环境变量和不必要的源码全文。凭据只存 credential handle；敏感会话内容遵循用户选择的持久化模式。

### 4.2 Append 规则

- Command append 时携带 `expectedSequence`；不匹配则拒绝，防止并发覆盖；
- `eventId` 幂等，重复提交不重复产生状态；
- `aggregateVersion` 只能递增；
- append 成功后再更新 materialized snapshot；
- snapshot 必须记录 `lastSequence` 和 projection hash；
- snapshot 损坏时从事件流重放；事件流损坏时 fail-closed 并保留旧项目备份。

## 6. 旧 `.slimemold` → 目标 schema 迁移

目标 schema 暂定为 v2；迁移器必须是独立、可测试、幂等的函数，不直接散落在 UI 或 Zustand action 中。

### 6.1 迁移步骤

1. 检测旧 `manifest/project.json` 版本和项目类型；
2. 校验旧结构，生成迁移前报告；
3. 将整个旧 `.slimemold` 复制到 `.slimemold/backups/<timestamp>/`；
4. 创建 v2 `manifest.json`，状态为 `migration-pending`；
5. 将 Project、Workflow、Agent、Default Agent、Control Snapshot、Issue、Pipeline、Orchestration、Run History 和 Checkpoint 转为事件；
6. 将 `projectControl.masterAgentId` 转为项目级 `ProjectMasterOverrideSet` 事件；
7. 将已有控制面记录按 `createdAt/updatedAt/approval` 重建为 Proposed/Approved/Superseded 事件；
8. 未知节点类型保存为 opaque legacy node，禁止在无 Adapter 时执行；
9. 从事件流重放生成 `snapshots/project-state.json`；
10. 对比迁移前后项目 ID、工作流数、节点数、Session 数、Issue 数、Run 历史和 Checkpoint 数；
11. 写入迁移报告和 `v1-to-v2.done`；
12. 任何一步失败都删除未完成的新结构、保留备份和旧项目，向用户显示可读错误。

### 6.2 兼容策略

- 旧项目第一次打开时迁移，不在后台静默破坏原文件；
- 迁移前显示项目路径、旧版本、备份位置和可能无法执行的节点；
- 迁移支持 dry-run；
- 旧 `projectControl` 字段缺失时生成默认事件，不阻塞旧工作流打开；
- 旧文件的未知字段放入 `legacy.extensions`，不能直接丢弃；
- 所有旧插件 Node 必须有 `pluginApiVersion` 和迁移/opaque 策略。

## 7. Runtime 重构目标

### 7.1 状态

```text
Task: proposed → approved → queued → running → succeeded
                                      ├→ failed → retrying → failed
                                      ├→ blocked
                                      └→ cancelled

Run: queued → running → partial / blocked / failed / cancelled / succeeded
```

`partial` 表示仍有独立任务完成，但至少有失败任务；`blocked` 表示依赖关系阻止继续；`failed` 表示运行级不可恢复或硬门失败；`succeeded` 必须有完整 Evidence 和验收结果。

### 7.2 Scheduler / Executor / Policy 分离

- Scheduler：只负责依赖满足、并发队列、阻塞传播和有限重试；
- Executor：调用 Provider/Node Adapter 并报告宿主可验证结果；
- Policy：决定目标模式、Agent 候选、重试上限和预算阈值；
- Evidence Collector：采集测试、diff、退出码、哈希和人工批准；
- Issue Sink：将失败、漂移、预算超限和需要人工接管转为 Issue；
- Recovery：根据事件流和 Checkpoint 重建未完成任务，保证幂等。

运行中的任何 `setState` 必须改为 Command → Event → Reducer，禁止 UI 直接把 Task/Run 状态写成成功。

### 7.3 重试和预算

- 每类 Task 有默认最大尝试次数；
- 退避时间和 Provider rate limit 由 Policy 给出，但宿主有上限；
- 预计消耗超过项目预算或触发高影响操作时生成 `AwaitingUser` 事件；
- 用户批准后生成 `ExecutionPolicyApproved`，而不是修改 Memory；
- push 偏好可以在全局/项目偏好中继承和覆盖；第一次启用高风险策略时记录一次明确风险确认，之后可自动执行，但只允许当前项目非 protected 分支、禁止 force push/发布/删除，并为每次 push 记录 Evidence。merge 可由管理类 Agent 按策略确认，用户保留一键收回权。

## 8. UI 重构目标

### 8.1 Simple / Project Cockpit

默认页面只展示：

- 项目身份和生命周期；
- 当前主控阶段；
- 当前待确认 Decision/Brief/Plan；
- 任务进度和 `partial/blocked/failed` 状态；
- 最近 Issue、Artifact、Run、Evidence；
- 继续会话、批准计划、查看执行草案；
- 进入 Agent Lab 或专业执行视图的项目上下文入口。

不默认展示 Provider、Token、节点参数、MCP、复杂路由和完整 DAG。

### 8.2 Agent Lab / Global Settings

全局设置负责：

- 全局 Agent library；
- Provider/Auth（含 Codex ChatGPT login）；
- 全局默认主控；
- 全局安全偏好和脱敏环境事实；
- 全局经验候选审核。

项目设置负责：

- 项目默认 Agent；
- 项目主控覆盖；
- 项目目标模式；
- 项目级 Route/Retry/Budget policy；
- 项目 Evidence 和执行权限。

每个字段在 UI 上标注 `Global`、`Project`、`Run override`，避免再次把项目配置称为全局配置。

### 8.3 Professional Execution Inspect

专业视图显示：

```text
Project context
→ Session / Decision / Brief / TaskGraph provenance
→ Pipeline / Workflow DAG
→ Task / Run / Checkpoint
→ Worktree / Diff / Test / Evidence
→ Issue / Drift / Recovery
```

所有按钮调用 Application Command，不直接修改 projection。专业用户可以替换 Projection 和工具面板，但必须读取 canonical state。

### 8.4 Convenience / friction budget

正常路径必须优先自动化，只有异常和高风险变化才暂停：

- 低风险项目将 Brief、Architecture、Task Graph 和执行准备合并为一次“确认计划并开始”操作；内部仍保留独立版本和来源事件；
- 用户批准计划后，宿主自动选择 Worker、创建独立 worktree、启动任务、运行测试和采集 Evidence；用户不手动绑定阶段 Workflow；
- `failed`、`blocked`、`partial` 在同一个恢复入口展示原因、影响、Evidence 和下一步动作，并提供重试/跳过/修改计划/恢复；
- Codex 登录状态可自动探测，首次配置提供一键启用全局 Codex 主控，不要求用户先理解 Agent/Provider/Global/Project 的内部层级；
- 记忆提升、迁移报告和低置信度诊断进入可稍后处理的批量收件箱，不阻塞交付；
- 全局/项目/Run override 的最终生效值始终在运行摘要中可见，显示来源和撤销入口。

## 9. Memory / Feedback 重构目标

### 9.1 候选生成

从以下来源生成候选：

- 用户显式评分、接受、修改、拒绝；
- 任务失败原因和人工接管；
- 测试工作流回归；
- Provider 成本、延迟、重试和成功率；
- 环境诊断，但只保存脱敏白名单字段。

### 9.2 作用域和提升

```text
Run / Session observation
→ Project MemoryCandidate
→ 用户反馈或安全白名单规则
→ Global Memory（可选）
→ 新项目首次执行时确认是否采用
→ ProjectExecutionPolicy / RoutingPolicy
```

全局 Memory 不能直接改变权限或副作用；它最多影响候选 Agent、提示词、目标模式建议和诊断提示。

### 9.3 “超过自己”的评分

交付硬门与偏好评分分离：

```text
Hard gate:
  acceptance criteria + tests + policy + evidence

Preference objective:
  cost-first / quality-first / speed-first / balanced

Feedback:
  accept / modify / reject
  satisfaction score
  modification magnitude
  rework reason
  token / latency / retry / intervention
```

系统保存同类任务的相对 baseline，不把某个时代的价格或模型名写死为永恒目标。任何自动调整都必须产生可解释的 Policy/Memory 事件，并支持回退。

## 10. 分阶段实施顺序

### Phase 0：基线与契约

**目标：** 不改变用户可见行为，先锁住设计和回退点。

- 只读审查当前 tracked diff 和未跟踪文件；
- 选择性创建 checkpoint commit；
- 新增 `src/domain/events.ts`、`src/domain/commands.ts`、`src/domain/state.ts` 的初版类型；
- 定义事件 JSON Schema、ID、版本、actor、source 和敏感字段规则；
- 定义 v1→v2 迁移报告格式；
- 为事件 append、expectedVersion、幂等和 reducer 写纯函数测试。

### Phase 1：A + 单 Worker 真实闭环

**目标：** 交付第一条真实用户路径，并完成一个受控 Codex Worker 任务，而不是停在只读草案。

- 将现有 `BeginnerExperience` 改为 Project Cockpit Projection；
- 主控调用统一走 Provider Adapter；
- Session/Brief/Decision/TaskGraph 用 Command → Event → Projection 更新；
- 低风险路径提供一次计划确认；只有高风险变化、预算超限、能力缺失和依赖阻塞才增加暂停/确认门；
- 生成 Execution Draft，并在用户批准后自动创建一个独立 worktree；
- 启动 Codex Worker，使用 Codex 自己的工具完成一个明确 scope 的代码任务；
- 宿主运行测试、采集 diff/退出码/Evidence，并生成 Task/Run 状态与 Issue 回流；
- 优先交付 Worker/worktree 自动化、Codex 一键配置和统一失败恢复入口；
- 增加重启恢复、来源追踪、跨页面一致性和 Worker 失败恢复测试；
- 使用已登录的 Codex provider 完成一次真实结构化主控响应和一次真实 Worker 响应验证。

### Phase 2：Runtime 内核

**目标：** 将当前执行器逐步迁移到统一 Run/Task 事件。

- 将 Scheduler、Executor、Policy、Evidence、Issue Sink 拆成独立模块；
- 先实现独立任务继续、依赖阻塞和 Run `partial`；
- 增加有限重试、预算暂停、取消、Checkpoint 和恢复；
- 保留 `workflowStore` facade，逐个把 action 改成 Application Command；
- 用事件回放替代直接恢复内存快照；
- 把现有执行器测试映射到新状态契约。

### Phase 3：C Agent Lab

**目标：** 把全局能力配置和项目能力引用分开。

- 从 SettingsCenter 拆出 Global Agent Library、Provider/Auth 和 Project Settings；
- 保留 Codex ChatGPT login 的官方 CLI 边界；
- 增加 Agent/Role/Prompt/Tool/Provider capability matrix；
- 增加全局默认主控、项目覆盖和 Run override 的清晰 UI；
- 将 memory candidate、feedback、objective policy 做成可审核 Projection。

### Phase 4：Schema Migration

**目标：** 在新 canonical schema 稳定后迁移旧 `.slimemold`。

- 编写 v1 validator、backup、dry-run 和 report；
- 编写控制面、Workflow、Run、Checkpoint、Issue、Plugin Node 转换器；
- 完成 replay hash 和数量一致性验证；
- 对未知 Node 提供 opaque legacy fallback；
- 在桌面端做真实旧项目迁移/恢复验收。

### Phase 5：Professional Extension Surface

**目标：** 开放专业扩展而不破坏宿主边界。

- 定义 plugin API version；
- 定义 capability manifest 和 permission review；
- 提供 Node/Provider/Policy/Memory/Projection 注册接口；
- 提供兼容性检查、禁用和回滚；
- 将旧插件逐步迁移到 Adapter/Command/Event 机制。

## 11. 测试和验收

- 事件 schema、sequence、aggregateVersion、幂等和 replay；
- 非法状态迁移被拒绝；
- 未批准对象不能执行；
- plugin capability 不能越权；
- secret 不会进入 event/project snapshot。

### A 薄闭环验收

- Codex/API/Ollama 至少一个 Provider 返回合法结构化响应；

## 12. 主要风险与取舍

- **事件流膨胀：** 只记录结构化事实，长文本分片/按策略保存，snapshot 可重建；
- **旧插件失效：** 先 opaque，再提供 Adapter，不在迁移时静默执行；
- **全局记忆污染：** 白名单、置信度、来源、过期和用户审核；
- **自动 push 越权：** 偏好与 ProjectExecutionPolicy 分离；用户可以持久化允许当前项目分支自动 push，管理 Agent 可按策略确认普通分支 merge，但宿主仍禁止 protected branch/force push/release/delete，并记录每次副作用；用户可以随时撤回管理 Agent 决策权；
- **Codex CLI 版本漂移：** 启动时探测能力和版本，JSONL parser 版本化，失败时 fail-closed；
- **一次性大重写风险：** `workflowStore` 保持 facade，按命令边界渐进迁移；
- **UI 与状态再次分叉：** Projection 只能读 canonical state，新增页面必须有对应 selector/contract test；
- **“所有实现可自定义”失控：** 开放 Adapter/Policy/Projection，不开放宿主状态和权限底层覆盖。

## 13. 当前待用户确认的决策门

开始 Phase 0 前还需要确认：

1. 是否采用本计划的 v2 事件字段和 `.slimemold/events/events.jsonl` 路径；
2. 是否把 `ProjectExecutionPolicy` 作为独立实体，而不是 Memory 的一个字段；
3. 是否接受 Codex provider 第一版只读、纯文本、单次最终响应的边界；
4. 第一阶段是否只迁移控制面，不迁移整个 Workflow executor；
5. checkpoint 是否只包含当前 Agent/Codex/全局主控相关 tracked 改动，所有图标和设计资产继续留在工作树但不纳入提交。

在这 5 项确认前，不进行大范围删除、重命名、自动迁移或 `workflowStore` 全文件重写。

## 14. 红队审查后的追加约束

三路独立红队审查确认，便利性改进不能绕过以下 P0 契约：

### 14.1 批准必须绑定不可变执行授权

`approved: true` 不足以代表用户批准了什么。新增 `ApprovalGrant` / `CapabilityGrant`，至少绑定：

- plan/task-graph/architecture 的内容 hash 和版本；
- effective ProjectExecutionPolicy hash；
- base commit、目标分支、worktree；
- Provider/Agent/插件版本和允许的 capability；
- 预算上限、自动 push 范围、管理 Agent merge delegation；
- actor、创建时间、过期/撤销状态。

新增宿主 Command：

```text
ApprovePlanAndEnqueueRun
→ 原子记录批准与 RunCreated
→ scheduler 自动领取
```

正常路径不再出现“批准计划后又点击一次普通 Run”的重复门。计划、策略、插件、基线或 capability 发生变化时，只让受影响授权失效并重新编译，不重复询问无关任务。

### 14.2 高风险偏好与授权分离，但不牺牲自动化

全局/项目设置可以持久化用户偏好的 `workspace-write` 或 `danger-full-access`，一次风险确认后同一 scope 的 Run 不重复打断。每次 Run 固化 effective policy 并写入审计。

以下变化才触发异常门：目标项目、分支、worktree、插件版本、能力范围、预算上限或策略 hash 发生变化。`danger-full-access` 仍必须在 UI 明示“非 OS 隔离”，不能被记忆自动扩大；项目偏好覆盖全局，但不反向修改全局。

自动 push 可由项目策略持续允许，但限于当前非 protected 分支、禁止 force push/release/delete，并做远端 lease 与推送后读回。管理 Agent 的 merge 权限是可撤销 delegation；用户的“禁止 Agent 决断”必须立即产生 generation fence，阻止尚未领取的 merge 动作。

### 14.3 Planner 与 Worker 分离

Codex 第一阶段拆成两个 Adapter：

- `MasterPlanner`：只读、纯文本/结构化输出，不接触项目文件；
- `WorkerExecutor`：明确的 worktree、写权限、工具、取消、超时、Evidence 和 recovery contract。

当前 7.11 的只读 Codex provider 不能直接宣称支持 Worker。Worker 启动前必须探测 Codex CLI 版本与能力；工具由 Codex 自己执行，第一版不桥接 SlimeMold ToolRegistry。

### 14.4 事件流必须单写入、可修复

项目事件流仍采用 `.slimemold/events/events.jsonl`，但必须增加：

- 项目级 writer lock 和跨进程串行化；
- append generation、checksum、fsync/原子提交标记；
- 半行/尾部损坏隔离，不静默丢弃；
- 写入失败后的 `needs-repair` projection；
- snapshot 记录 lastSequence/projectionHash，可从事件重建；
- 所有旧 snapshot 导入事件标记为 `migration/synthetic`，不伪造原始批准历史。

当前项目控制面解析遇到损坏数据时不能继续返回一个看似正常的空项目；必须保留原始数据，允许只读查看、导出、修复或回滚。

### 14.5 恢复必须识别未知副作用

每个文件写入、测试、push、merge 和外部调用先记录 intent，再记录 receipt：

```text
SideEffectPlanned
→ SideEffectStarted
→ SideEffectReceipt / SideEffectUnknown
```

Receipt 绑定 idempotency key、目标、输入 hash、策略 hash 和宿主观测结果。崩溃后只有明确幂等且结果已知的动作才能自动恢复；未知动作进入恢复向导，不能用重复执行换取“顺畅”。Checkpoint 还必须绑定 workflow/graph/node/plugin/input/policy hash，不能只按节点 id 复用结果。

### 14.6 用户便利性红队修正

第一阶段除既定三项优先级外，还要修正：

- 所有创建入口汇入“开始项目”；鬼点子先进入一字段 Idea Inbox，不立即创建正式 Project/Issue；
- 低风险的 Brief/架构/TaskGraph/编排合并为一个可展开计划审查；
- 初学者只看到“目标、方案、待做、执行中、已检查/需决定”；内部实体名词和 ID 进入详情；
- 澄清提供按推荐、先做最小版、以后决定、暂停和预计剩余轮次；
- Brief/计划支持字段级修改、退回、diff、supersede 和撤销；
- 失败/blocked/partial 统一进入恢复卡，不要求用户去 Issue、DAG、日志之间寻找原因；
- 项目记忆在驾驶舱可查看/编辑/忘记，全局提升进入非阻塞批量审核；
- Issue 自动去重/聚合，支持批量 triage；
- 迁移默认备份 + dry-run + 一键继续/只读打开/稍后处理，技术细节放高级报告；
- 全局/项目/Run 的最终生效策略、Agent、能力和来源始终可见。

### 14.7 调整后的实施顺序

```text
Phase 0a：canonical event / ApprovalGrant / ExecutionPolicy 契约
→ Phase 0b：writer lock / replay / migration synthetic baseline / side-effect receipt
→ Phase 1a：统一“开始项目”与一次计划审查
→ Phase 1b：Codex 一键配置 + 单 Worker/worktree 真实闭环
→ Phase 1c：统一失败恢复与 partial/blocked 传播
→ Phase 2：多 Worker、完整 Runtime、记忆/评估和专业扩展
```

不能先做“漂亮首页”再补这些契约；也不能先把 `workflowStore` 整体重写后再寻找用户闭环。
