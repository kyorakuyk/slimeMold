# SlimeMold 2.0 · AI 软件项目交付操作系统

> SlimeMold 不是一个“有很多 Agent 的聊天应用”，也不是一个通用的节点式 AI Playground。
> 它的目标是：让一个人能够借助一套可审计、可度量、可人工接管的 AI 组织，持续完成软件项目的规划、生产、交付和维护。

当前仓库处于**产品重定位中的 alpha 阶段**。下面描述的是 2.0 的产品方向；其中一部分已经有代码基础，另一部分仍在实现或验证中。不要把愿景当成当前能力，也不要把 headless 冒烟当成生产级自治证明。

## 一句话

SlimeMold 把用户的产品目标转化为：

```text
产品方案 → 软件架构 → 可执行任务 → 模型调度 → 隔离生产 → 自动测试 → 审计验收 → 持续维护
```

用户是项目所有者和最终决策者；SlimeMold 提供一套虚拟的管理层、生产层和审计层，帮助用户把模糊想法变成可交付的软件结果。

## 设计灵感：从自动化游戏到 AI 软件工厂

SlimeMold 的最初灵感来自自动化和工厂建造类游戏。

这不是给软件套一层游戏皮肤，而是借用自动化游戏中最有价值的系统心智模型：

```text
订单 → 配方 → 生产线 → 资源调度 → 瓶颈优化 → 质检 → 出货 → 维护与扩产
```

在 SlimeMold 中，它对应为：

| 自动化游戏概念 | SlimeMold 概念 |
|---|---|
| 玩家 | 项目所有者 / 产品负责人 |
| 订单 | 用户需求 / Issue |
| 工厂蓝图 | 产品方案 / 软件架构 |
| 生产线 | Agent 工作流 |
| 机器 | Agent、模型和工具 |
| 机器参数 | 成本、速度、质量、上下文和能力 |
| 半成品 | PRD、架构、任务、代码模块 |
| 质检 | 测试、审计、diff 和验收 |
| 仓库 | 项目记忆、Artifact 和 Issue |
| 瓶颈 | 阻塞任务、冲突、昂贵模型和人工审批 |
| 科技树 | 经过验证的 Prompt、模型策略和任务模板 |
| 出货 | 软件交付和发布 |
| 维护 | Bug、回归、增量任务和版本迭代 |

游戏感应该来自真实的系统反馈，而不是装饰性的徽章和动画：

- 任务是否更快完成；
- 生产线哪里堵塞；
- 哪种模型在什么任务上更划算；
- 一次失败造成了多少返工；
- 自动化程度是否提高；
- 下一次同类任务是否更快、更便宜、更稳定。

因此，SlimeMold 提供三种使用层级：

1. **工厂视图**：普通用户只看到订单、进度、预算、瓶颈、风险和交付物；
2. **管理视图**：产品负责人查看方案、架构、任务队列、模型分配和审计报告；
3. **工作流视图**：专业用户查看节点、连线、并发、控制流、worktree 和证据。

默认目标不是让用户学习如何配置一座复杂的虚拟公司，而是让用户提出一个目标后，看到一座真正开始生产软件的工厂。所有游戏化反馈最终都必须对应真实的项目交付结果；如果只有角色、状态和动画，没有更高的质量、更低的成本或更少的人工时间，那就只是模拟器，不是生产系统。

## 它解决什么问题

单个 Coding Agent 可以完成一次代码修改，但一个持续的软件项目还需要处理：

- 需求是否清楚，产品方向是否值得做；
- 功能如何划分，模块之间如何衔接；
- 哪些任务应该并行，哪些任务必须串行；
- 什么任务用便宜模型，什么任务值得使用高性能模型；
- 代码是否真的通过测试，而不是只生成了看起来合理的文本；
- 每次修改花了多少钱、多少时间、多少次返工；
- 项目完成后如何进入 Issue、维护和下一轮迭代。

SlimeMold 的核心不是“模拟公司角色”，而是把上述过程变成有输入、有输出、有证据、有审批的项目交付系统。

## 目标用户

第一阶段不面向所有 C 端用户，也不试图替代所有开发工具。

优先服务：

- 独立开发者；
- 技术型产品创始人；
- 需要用较低成本完成软件原型和迭代的小团队；
- 需要本地执行、代码隔离、人工审批和成本审计的研发团队。

非技术用户最终可以只看到“目标、方案、进度、待审批事项和交付物”，但当前版本仍然要求使用者理解项目、代码和测试边界。

## 它不是什么

当前阶段明确不把 SlimeMold 定位为：

- ComfyUI 的通用视觉生成替代品；
- n8n 的通用业务自动化替代品；
- Dify 的云端 Agent 平台替代品；
- Cursor、Claude Code 或 Codex 的简单复制品；
- 无需用户确认的自动公司；
- 对恶意 Agent 或恶意插件提供完整操作系统级隔离的安全沙箱。

节点图是高级控制和调试界面，不是普通用户必须学习的主入口。

## 交互与控制面架构（2026-08-31）

当前产品入口不再把“新建项目”理解为打开一个空白工作流，而是让用户先进入一个项目级主控会话。主控 Agent 负责需求澄清、项目记忆、结构化产物和确认门；管理层把已确认的目标编译为任务图；生产层再将任务图落实为 Pipeline、Orchestration 和 Workflow DAG。

三种用户视图是同一项目状态的不同投影，而不是三套独立系统：

```text
项目会话 / 主控
  → Issue、Decision、Product Brief
  → PRD、Architecture、Task Graph
  → Pipeline / Orchestration
  → Workflow DAG / Worker
  → Run、Evidence、Artifact
  → Bug、风险、运维 Issue 回到会话和 Issue 工作台
```

产品页面按认知难度分为：

1. **简易工作台**：用户目标、主控问询、项目状态、待确认决策和交付物；
2. **Issue 工作台**：全局收件箱、项目归属、待做队列、执行中任务和已交付/运维任务；
3. **专业 DAG 工作台**：节点、连线、并发、权限、worktree、测试和证据。

没有当前项目时，首页不直接强调高级工作台，而应以“开始项目会话”为主动作。存在当前项目时，首页显示该项目的会话状态、下一步、Issue 和交付物；进入专业视图必须携带当前项目上下文。详细的数据实体、版本、映射和审批规则见[项目控制面架构](docs/PROJECT_CONTROL_PLANE_ARCHITECTURE.md)。

### 用户层

用户可以提出自然语言目标、约束和预算。用户最终批准：

- 产品方向和范围；
- 计划和架构；
- 高风险或高成本任务；
- 代码合并、发布和破坏性清理。

主控 Agent 可以提出建议，但不能把建议伪装成用户决策。

### 管理层

管理层输出结构化项目资产，而不是只输出聊天文本：

- `Product Brief`：目标用户、问题、价值、约束；
- `PRD`：功能范围、非目标和验收标准；
- `Architecture Spec`：模块、接口、数据流和技术边界；
- `Task Graph`：可执行任务、依赖、影响域和负责人；
- `Risk Register`：风险、阻塞条件和升级路径；
- `Cost Budget`：模型、预算、预计耗时和人工审批门槛。

### 生产层

生产任务必须具备明确的：

- 输入和输出；
- 允许修改的路径；
- 影响域和依赖；
- 测试方法；
- 验收规则；
- 失败和返工路径。

生产层可以并行，但并行不等于无约束。存在共享影响域的任务必须串行化或进入冲突协调流程。

### 审计层

审计员不能只报告“节点 success”。它要记录：

- 使用的模型和 Prompt；
- 输入输出 token、成本和耗时；
- 首次通过率；
- 返工次数；
- 失败原因；
- 测试和 diff 的真实结果；
- 人工介入时间；
- 最终是否被用户接受。

审计结果只能由宿主和真实运行结果生成。Agent 自己写的“测试通过”或“任务完成”不能成为事实证据。

## 模型经济学

SlimeMold 不把“最贵模型”当作默认答案，也不把“最便宜模型”当作唯一目标。

一次任务的模型选择应近似于：

```text
最小化：直接调用成本
      + 预计返工成本
      + 延迟成本
      + 失败风险成本
      + 人工复核成本
```

任务画像至少包含：

- 任务类型；
- 复杂度和歧义程度；
- 上下文长度；
- 是否需要多模态能力；
- 是否涉及核心架构或安全边界；
- 是否容易自动测试；
- 截止时间和预算。

模型画像至少包含：

- 输入输出价格；
- 延迟；
- 工具调用和代码能力；
- 多模态能力；
- 上下文能力；
- 按任务类型统计的成功率、返工率和平均成本。

“UI 用某个模型、复杂代码用某个模型”只能是初始假设，不能是长期策略。长期策略必须来自真实项目数据。

多 Agent 裁定只用于高风险、高歧义或返工代价高的任务。简单任务默认直接执行，避免把成本和延迟浪费在组织表演上。

## 记忆与经验

### 项目记忆

项目记忆保存当前项目的：

- 目标和约束；
- 已批准的产品与架构决策；
- 关键接口和不变量；
- 已知问题和踩坑；
- 运行结果、成本和验收记录。

### 全局经验

全局经验不是所有项目的原始聊天记录集合。只有经过整理、脱敏、验证和批准的策略才能跨项目使用。

每条经验应保留：

- 来源任务和项目范围；
- 适用条件；
- 证据和样本量；
- 置信度；
- 创建和失效时间；
- 是否经过人工批准。

没有证据的“自我进化”只是错误传播。当前版本不承诺自动把任意项目经验写入全局策略库。

## Issue 与维护生命周期

Issue 不直接进入执行。它必须经过：

```text
想法
→ 规划中
→ 候选需求
→ 用户批准
→ 待做
→ 在做
→ 待验收
→ 已完成
→ 维护中
```

主控 Agent 可以从项目记忆和 Issue 中提出候选需求，但只有用户批准后才能进入管理层和生产层。

项目完成后，系统从“构建模式”进入“维护模式”：

- 接收 Bug 和用户反馈；
- 分析影响范围；
- 生成增量任务；
- 复用既有架构和测试；
- 输出补丁、回归结果和成本报告。

外部自动化平台可以作为连接层，但 SlimeMold 负责项目目标、任务、Artifact、验收和维护状态的连续性。

## 当前技术架构

```text
src/
├── engine/         # 图计划、拓扑分层、并发调度、缓存、事件、checkpoint
├── agents/         # Provider、AgentRouter、模型经济、Harness、经验记录
├── orchestrator/   # 管理层编排：草案、确认门、阶段执行
├── nodes/          # 产品、派发、worker、协调、交付等节点定义
├── dev/            # H4：worktree、受控修改、命令、证据、确定性验收
├── store/          # 项目、工作流、运行态和持久化状态
├── canvas/         # React Flow 画布与高级工作流视图
├── components/     # 项目驾驶舱、任务、审计、设置和面板
└── plugins/        # 实验性的本地插件能力

src-tauri/
└── src/lib.rs      # Tauri 宿主、凭据、文件权限和 H4 受控命令通道
```

执行主链：

```text
工作流图
→ 子图展开
→ data/control 分离
→ Kahn 拓扑分层
→ scope 冲突簇规划
→ 并发节点执行
→ 能力裁剪
→ AgentRouter / Provider
→ 缓存 / 日志 / 成本 / 事件
→ checkpoint / Evidence / 验收
```

## 安全边界

- H4 的默认目标是受控开发和宿主证据链，不是恶意进程的完整隔离。
- Worktree 中的修改必须经过路径策略、真实测试、diff 和人工确认。
- 正常清理必须绑定验收、基线和工作区状态；失败时保留现场。
- 不允许自动 push，不允许把 Agent 自报结果当作宿主证据。
- 插件默认视为可信本地代码；不要安装来源不明的插件。
- 不要把明文 API Key 写入工作流文件、项目仓库或共享日志。
- 当前路线仍以桌面端 Provider/宿主通道为主，完整的 Rust 侧图执行后端尚未实现。

## 发展路线

> **当前执行主线**：Phase 0 产品收缩 → Phase 1 单项目交付闭环 → Phase 1.5 项目会话与映射控制面 → Phase 2 经验和经济性闭环 → Phase 3 Issue 与维护 → Phase 4 持久运行时。
> 下方“环境联动与创作生态”只是单独记录的远期 Idea，不属于当前 Phase，不构成版本承诺，也不应据此安排近期开发任务。

### Phase 0：产品收缩

- 以软件项目交付作为唯一主线；
- 把项目驾驶舱作为主入口；
- 创意、媒体、插件和通用 Playground 功能移出默认产品；
- 冻结新增 Provider 和自由 DAG 能力；
- 固化安全、验收和数据模型。

### Phase 1：单项目交付闭环

```text
目标
→ Product Brief
→ PRD / Architecture
→ 用户确认
→ Task Graph
→ 模型路由
→ worktree 生产
→ 测试与 diff
→ 审计报告
→ 用户批准交付
```

### Phase 1.5：项目会话与映射控制面（当前设计）

这一阶段解决“用户无法仅通过自然语言启动完整项目”的入口问题：

- 从项目级会话开始，而不是从空白 Workflow 开始；
- 主控 Agent 通过有限的高价值问询形成 Product Brief、Decision 和未决问题；
- 管理层输出 PRD、Architecture、Task Graph、Risk Register 和 Cost Budget；
- 用户确认后，复用 H3 Orchestrator 生成 Pipeline 和执行计划；
- 增加 Issue 的全局收件箱、项目归属、队列和运行反馈；
- 将 Issue、Task、Stage、Workflow、Run 和 Artifact 通过稳定 ID、版本和来源互相映射；
- 空白首页不直接暴露高级工作台，项目首页的专业入口必须携带当前项目上下文。

本阶段先建立数据模型、会话状态机、确认门和最小 UI 闭环，不承诺立即实现无人值守的多部门自治。

### 远期 Idea：环境联动与创作生态（暂不进入开发路线）

> 这是产品探索记录，不是当前路线。它只有在核心软件交付闭环被验证、出现明确用户需求和可承担的运行成本后，才值得重新评估。

如果未来重新立项，方向可能不是做“本地权限更大的 n8n”，而是把本地能力变成普通用户可以理解、组合、分享和复用的创作材料。

核心对象是 `EnvironmentProfile`：

```text
我的本地环境
├── 已安装模型：Ollama / 云端 Provider
├── 开发工具：Git / Node / Python / Docker
├── 本地文件夹和资产
├── MCP 服务和其他连接器
├── 浏览器与桌面应用
├── 可用权限
├── 依赖版本
└── 运行健康度
```

每座工厂都声明自己的环境依赖，而不是让用户面对底层配置：

```text
工厂蓝图
├── 需要哪些连接器
├── 需要哪些权限
├── 是否需要网络
├── 是否支持离线模拟
├── 预计成本和耗时
├── 输入与输出格式
├── 风险等级
└── 版本与兼容范围
```

用户界面按认知难度逐步展开：

1. **工厂总览**：看到订单、生产线、数据流、瓶颈、成本和真实产出；
2. **任务看板**：管理规划中、待做、进行中、待验收、已完成和维护中的任务；
3. **专业 DAG**：编辑节点、MCP、Agent、上下文、权限、并发和审计规则。

如果未来重新立项，可以考虑同时保留两种运行模式：

- **模拟模式**：免费、离线、无需 API Key，用于教学、试错和游戏化体验；
- **真实模式**：连接用户自己的模型、文件、账户和项目，产生真实文件、数据或内容。

游戏性必须来自真实的系统反馈：生产速度、成本、质量、返工、瓶颈和用户自定义 KPI，而不是虚假的积分。用户可以逐步把自己的收获接入仪表盘，例如文章阅读、视频播放、GitHub 项目数据或其他可授权指标；初期优先支持手动输入、CSV、RSS、Webhook 和少量稳定连接器，不承诺一次覆盖所有平台。

#### 创意工坊与可分享内容

Steam Workshop 的定位是**公开内容分发和订阅入口**，不是后端数据库。Steam Cloud 的定位是**有限的按应用文件同步**，不是通用服务器、私有项目数据库或后台任务队列。私有项目记忆、运行记录、凭据和长期任务状态必须保存在本地数据库或未来的独立服务中。

优先分享以下声明式内容：

- 工厂蓝图；
- 任务配方；
- Prompt 与 Agent 角色卡；
- 模型路由策略；
- KPI 仪表盘；
- UI 主题；
- 教程关卡；
- 模拟订单和项目模板；
- MCP/连接器的依赖声明。

任意 JavaScript、Shell、文件读写、网络访问、API Key 和私人项目记忆不默认进入创意工坊执行。高风险 Custom Node 只能在明确的开发者模式中启用，并显示权限、依赖和风险。

#### 免费本体与专业扩展

免费本体必须脱离付费 AI 也能完成基础体验：工厂总览、模拟生产、教程、基础蓝图和本地导入导出。

专业扩展可以提供：

- 真实 AI 执行；
- 高级 DAG；
- 本地环境管理；
- MCP 和专业连接器；
- 项目审计与成本分析；
- 任务维护和增量执行；
- 专业蓝图与内容包。

一次性 DLC 不能承担无限的第三方模型成本。真实 AI 模式初期采用 BYOK（用户自带模型凭据），以后再考虑云端额度或订阅服务。

### Phase 2：经验和经济性闭环

用真实运行结果测量不同模型、Prompt、Agent 组合和工厂蓝图的：

- 成本；
- 耗时；
- 首次通过率；
- 返工率；
- 人工介入时间；
- 最终验收质量；
- 对用户 KPI 的实际影响。

只有具备来源、样本、证据、置信度和失效时间的经验，才允许提炼为跨项目策略。没有真实结果数据，不扩展“自我进化”叙事。

### Phase 3：Issue 与维护

- 需求候选和用户审批；
- Issue 到任务的转换；
- 增量 worktree 修改；
- 回归测试和维护报告；
- 项目之间的受控 Artifact 传递。

### Phase 4：持久运行时

在确有长期任务需求后，再引入本地 daemon 或远程 Worker：

- 持久任务队列；
- 崩溃恢复；
- 幂等和锁；
- 预算和并发配额；
- 通知与权限；
- 项目级和团队级审计。

## 继续投入的验收标准

SlimeMold 不以“节点数量”或“Agent 数量”判断成功，而以真实交付结果判断。

至少需要证明：

1. 使用 SlimeMold 完成真实软件任务时，质量不低于强 Coding Agent 基线；
2. 在相同质量下，模型成本或人工时间有明确下降；
3. 任务、成本、返工和验收结果可以被解释；
4. 用户愿意把下一个项目继续放进来；
5. 失败任务可以回到人工决策，而不是无限自动重试。

如果做不到这些，SlimeMold 应该作为个人研发工具保留，而不是继续扩展为更复杂的“虚拟公司模拟器”。
