# SlimeMold 产品哲学：项目级元 Harness

> 本文定义 SlimeMold 为什么这样设计，以及产品和架构选择需要遵守的上位原则。
> 它不是功能清单、实现说明或当前完成度报告。某条原则写在这里，不代表当前代码已经完全实现；实现状态应以架构文档、测试和开发日志为准。

## 0. 来源、归属与共识状态

本文明确区分三种内容，避免把助手的解释误写成用户原话：

### 0.1 用户明确提出的原始哲学

以下原则来自用户对 SlimeMold 的直接定义，是本产品哲学的原始来源：

- SlimeMold 是比单个 Agent Harness 更大的项目级元 Harness，同时约束用户与 Agent、Agent 与 Agent、成员与项目之间的交流和权限边界；
- 通过约束交流方式和按需暴露上下文，尽可能降低用户或单个 Agent 的错误判断对项目造成的影响；
- 每个成员只应获得完成职责所需的上下文和信息；
- 用户拥有溯源的权力和能力，高级工作台因此必须存在；
- 任务依靠内部数据流和项目事实执行，而不是依靠高级工作台的节点图直接执行；
- 可视化模块把内部工作流解释成用户能够理解的视觉板块，高级视图是解释层和溯源层。

### 0.2 助手独立提出的判断

以下是助手基于上述哲学提出的独立推导，不自动等同于用户原始观点：

- SlimeMold 的核心价值是“受托执行”，而不是无限自治；
- 用户保有目标和最终决策权，Agent 只有局部推理和执行权，系统负责上下文、权限、状态、证据和恢复；
- 信任应建立在系统能够证明结果，而不是模型自报成功；
- 失败和未知副作用应当是一等状态；
- 元 Harness 应比 Agent 更确定、可审计、可恢复，控制面不能依赖另一个不可解释的 Agent 黑箱；
- 表层界面应尽量简单，内部治理和事实链必须严格。

### 0.3 当前已经形成的共同共识

经过本轮讨论，双方目前可以共同采用以下原则作为设计基线：

```text
用户拥有目标和最终决定权，但模糊意图不能直接产生不可逆事实。

Agent 可以推理和施工，但不能凭文本定义项目事实或宣布成功。

系统负责编译上下文、编排权限、约束通信、维护状态、验证结果和提供溯源。

按需暴露同时适用于信息、行动和解释权限。

高级工作台解释内部数据流和项目事实，但不是任务执行的唯一事实源。

所有视图都可以不同，但必须投影同一组项目事实。

失败现场应被保留、解释和恢复，而不是被隐藏或猜测成成功。

图与内部语义实现通过中间语义层双向映射；图上操作先转换为语义意图或领域命令，不能直接改写运行事实。

图应区分可编辑的 Draft Graph、版本化可复用的 Static / Published Graph，以及某次 Run 的 Dynamic Runtime Graph。

任务边界以可勾选、可验证的 Boundary Contract 传递；子任务只能收窄上级边界，不能自行扩大能力。
```

第 1 节及之后是对上述三类内容的工程化转译，是当前共同设计稿，不应被引用为某一方的逐字原话。未来新增原则时，应先标注来源；只有经过双方确认，才进入“共同共识”。

## 1. 核心命题

Agent Harness 通常负责驾驭一个大模型：提供上下文、限制工具、控制循环、检查输出，并把模型的不确定性放在一个可控的执行边界内。

SlimeMold 需要建立更大的 Harness：

```text
用户
  ↕  意图、决定、解释、批准
Project Harness
  ↕  上下文、权限、通信、状态、证据、恢复
Agent / Worker
  ↕  推理、提案、局部执行、结果
项目
```

因此，SlimeMold 不是单纯约束 Agent 的执行器，而是同时约束：

- 用户与 Agent 如何交流；
- Agent 与 Agent 如何交流；
- 每个成员能够知道什么；
- 每个成员能够决定和执行什么；
- 一个局部判断如何影响整个项目；
- 一个结果如何成为可被项目接受的事实。

系统约束的不是用户的合法目标，而是防止模糊意图、局部推理或未经验证的结果直接产生不可逆的项目事实。

## 2. 产品真正要治理的对象

SlimeMold 的基本对象不是一次 LLM 请求，也不是一张可视化节点图，而是一个：

> 有目标、有边界、有依赖、有版本、有验收标准，并且可以暂停、恢复和交付的项目任务。

系统需要持续回答五个问题：

```text
谁提出了这个目标？
谁批准了这个决定？
谁可以看到哪些上下文？
谁可以执行哪些动作？
什么证据证明结果已经发生？
```

这使 SlimeMold 的中心从“模型调用编排”转向“项目中的认知与行动治理”。

## 3. 用户、系统与 Agent 的权威边界

### 3.1 用户

用户拥有：

- 项目的目标和最终方向；
- 对高影响决策的批准权；
- 对项目事实的查看和溯源权；
- 对自动化边界的收回和调整权；
- 对最终交付、合并、发布和破坏性清理的决定权。

用户不应因为一句模糊表达，就意外触发不可逆副作用。系统应把高影响意图转化为明确的 Decision、Command、Approval 或 Plan Revision，再执行后续动作。

### 3.2 Project Harness

系统负责：

- 将自然语言意图收敛为结构化计划；
- 依据职责和风险编译上下文；
- 编排信息权限和操作权限；
- 约束用户与 Agent、Agent 与 Agent 的通信契约；
- 维护项目事实、版本、状态和来源；
- 让执行结果经过宿主验证；
- 保留失败现场和未知副作用；
- 将内部事实投影为不同认知层级的界面。

元 Harness 本身应尽量确定、持久、可重放、可审计。Agent 可以不确定，但控制面不能依赖另一个不可解释的 Agent 黑箱来决定事实。

### 3.3 Agent / Worker

Agent 可以：

- 理解分配给它的目标；
- 提出方案和风险；
- 请求必要的上下文；
- 在授权范围内修改代码或生成 Artifact；
- 报告成功、失败、阻塞和不确定性。

Agent 不拥有：

- 项目事实定义权；
- 用户决策批准权；
- 超出任务范围的隐式权限；
- 以自然语言宣布任务成功的权力；
- 覆盖旧计划、旧 Evidence 或其他 Worker 事实的权力。

### 3.4 Host Acceptance

宿主负责回答：

```text
结果是否真实存在？
结果是否符合验收标准？
路径和权限是否符合策略？
副作用是否有 receipt？
```

模型文本可以作为解释和候选结果，但不能取代宿主 Evidence、Receipt 和真实代码状态。

## 4. 按需暴露：最小上下文与最小权限

“按需暴露”不是单纯隐藏高级功能，而是同时应用于信息、行动和解释三个层面。

### 4.1 信息最小权限

Worker 只应收到完成当前任务所需的：

- 任务目标和非目标；
- 相关 Decision、Architecture 和 TaskGraph 版本；
- 影响文件和符号；
- 必要的依赖接口和文档；
- 验收标准；
- 允许访问的路径和工具；
- 与当前任务相关的历史经验。

不应默认把整个仓库、所有聊天记录和全部项目记忆灌给 Worker。

### 4.2 行动最小权限

能够读取不等于能够写入，能够写入不等于能够执行，能够执行不等于能够产生外部副作用。

```text
可读范围
  ⊇ 可写范围
      ⊇ 可执行范围
          ⊇ 可产生副作用的范围
```

权限应绑定到 Task、Policy、Worktree、工具和风险级别，而不能只绑定到 Agent 名称。

### 4.3 解释最小权限

Worker 不应被迫对不属于它职责的内容做全局推断。例如，负责修改 UI 的 Worker 可以报告架构风险，但不能自行决定数据库、部署路线或项目范围已经改变。

如果上下文不足，Worker 应提出结构化的上下文请求，而不是猜测或越权读取整个项目：

```text
缺少信息
→ 需要它的原因
→ 请求的最小范围
→ 如果无法获得信息的风险
```

## 5. 通信契约

### 5.1 用户 → Project Harness

用户消息首先是意图、问题或候选决定，不自动等价于批准的项目事实。

```text
用户表达
→ 意图 / 假设 / 决策提案
→ 影响范围与风险
→ 用户确认
→ Decision / Plan Revision / Command
```

高影响内容至少包括：

- 改变项目目标或非目标；
- 改变架构、接口或数据模型；
- 改变预算、权限或 Provider；
- 启动代码修改；
- 合并、发布、删除或外部写入。

### 5.2 Project Harness → Agent

系统不应把完整项目历史转发给每个 Agent，而应发送结构化 Task Contract：

```text
目标
非目标
输入事实与来源
依赖
影响范围
允许能力与权限
输出格式
验收标准
预算与超时
失败处理方式
```

### 5.3 Agent → Agent

Agent 默认不直接共享完整聊天记录，而通过项目 Harness 交换结构化产物：

```text
Proposal
Artifact
Decision Request
Evidence
Receipt
Failure / Blocker
```

Agent A 的提议必须经过来源和权限判断后，才能成为 Agent B 的输入。两个 Agent 的私下共识不能自动升级为项目决策。

### 5.4 执行结果 → 项目事实

Worker 报告的是候选结果；宿主验收、事件记录、Git 状态和 Receipt 决定哪些内容能够进入项目事实。

## 6. 事实、权威与溯源

SlimeMold 应明确区分不同类型的权威：

```text
DomainEvent stream       → 状态迁移事实
Decision / Plan Revision → 用户批准的方向事实
Host Evidence / Receipt  → 执行与副作用事实
Git revision / worktree  → 代码状态事实
ProjectFile / snapshot   → 投影与恢复材料
Agent text               → 建议、解释或候选结果
```

任何用户可见的结论，都应能在需要时向下追溯：

```text
项目目标
→ Decision
→ Architecture / Task
→ Run
→ Worker
→ Worktree / revision
→ Command
→ Evidence / Receipt
```

溯源不意味着用户必须一直看到全部细节。它意味着系统默认保持简洁，但不能剥夺用户检查事实的权力。

## 7. 视图是投影，不是执行事实源

SlimeMold 的任务执行依靠内部数据流、领域状态和持久化事实，而不是依靠用户在画布上看到的视觉连线。

```text
内部数据流 / DomainEvent / Runtime
              ↓
      Cockpit / Issue / DAG / Audit
              ↓
        用户理解与受控操作
```

### 简易驾驶舱

展示：

- 项目目标；
- 当前阶段；
- 系统理解；
- 待确认决定；
- 当前风险；
- 下一步动作；
- 可理解的结果和恢复选项。

### Issue 工作台

展示项目中的变化、问题、风险、阻塞和交付状态，是计划和反馈的工作面。

### 专业 DAG 工作台

展示：

- Task、Stage、Workflow 和 Run 的关系；
- Worker、worktree 和 base revision；
- 测试、diff、Evidence 和 Receipt；
- 事件、版本和恢复细节。

它的定位是**执行解释、调试、审查和溯源面**，不是任务事实的唯一来源。专业视图可以发起受控命令，但不能绕过领域状态机直接改变运行事实。

如果用户在图上编辑计划，系统应产生新的 Plan Revision 或领域命令，而不是静默改写正在运行的任务。

### 7.1 图是可交互的语义投影

“视图不是事实源”不等于“视图只能只读”。用户可以在图上表达修改意图，但该意图必须经过语义转换和控制面验证：

```text
用户拖动 / 修改节点
→ 图操作解释器
→ 语义意图 / Domain Command
→ Plan IR 或 Plan Revision
→ 事件流与内部状态
→ 重新生成各类视图
```

图层不应直接把 React Flow 的局部状态写入运行时。每个可执行节点都应能追溯到来源对象、来源版本和运行实例；运行时展开出来的临时节点不能反向静默修改原始计划。

用户操作至少分为三类：

| 图上操作 | 语义 | 是否影响执行事实 |
|---|---|---|
| 移动、缩放、分组、颜色 | 视图投影修改 | 否 |
| 增加节点、修改参数、调整连线 | 计划草案或计划变更 | 经过命令/版本后才影响 |
| 修改权限、能力、验收、发布或删除策略 | Decision / Policy / Acceptance 变更 | 必须经过更高等级确认 |

### 7.2 图的三个生命周期

为了同时支持编辑、复用和运行，不能只区分“静态图”和“动态图”，还需要一个可编辑的草案态：

```text
Draft Graph
  → 用户或 Agent 编辑、试验、审查
  → publish
Static / Published Graph
  → 按固定版本引用和组合
  → instantiate
Dynamic Runtime Graph
  → 某次 Run 的实际展开、分支、重试和证据投影
```

#### Draft Graph

Draft Graph 是尚未成为运行事实的计划语言，可以被用户和 Agent 修改、分叉、废弃和重新评估。

#### Static / Published Graph

Static Graph 是经过命名、版本化和边界声明的可复用 Graph Module。它可以在父图中作为一个节点，避免重复造轮子，也给用户提供实验和复用空间。

静态图对父图可以是黑盒，但对拥有溯源权的用户不能是不可解释的黑盒。父图至少能够看到模块版本、输入输出、能力、权限、成本、状态和 Evidence 摘要；用户可以按权限下钻查看内部定义。

#### Dynamic Runtime Graph

Dynamic Runtime Graph 是某次 Run 根据静态模块、输入、策略和上下文实例化的执行图，可能包含条件分支、循环、fallback、retry、临时验收和运行实例。它主要用于观察、调试和溯源，不应被直接当作新的源计划。

双向映射不保证所有运行节点都能一一反向编辑，因此必须保存：

```text
moduleId / moduleVersion
→ sourceGraphId / sourceGraphVersion
→ sourceNodeId
→ runtimeInstanceId / attempt
→ Evidence / Receipt
```

### 7.3 静态图模块与插件节点

插件节点可以是 Static Graph Module 的一种分发和实现形式，但二者不是同义词：

```text
Graph Module → 语义上的可复用能力模块
Plugin        → 模块的安装、分发、manifest 和实现包装
```

Static Graph 可以由内置工作流、插件 Worker、外部 Runtime 或普通代码实现。无论实现方式如何，父图都应通过稳定的 `moduleId@version` 引用，并在模块边界暴露输入输出、能力、权限、副作用和验收契约。

## 8. 渐进式透明

SlimeMold 应同时满足两类需求：

```text
普通用户：我现在需要知道什么？
专业用户：我能否追溯系统为什么这样做？
```

因此，界面应遵循：

```text
默认只呈现当前决策所需的信息
→ 用户可以向下展开原因和影响
→ 用户可以查看原始 Artifact、Event、Command 和 Evidence
→ 用户可以回到高层叙事继续做决定
```

透明度不是一次性倾倒所有日志，而是让每个结论拥有可展开的来源链。

## 9. 失败与恢复哲学

失败不是需要隐藏的异常，而是项目生命周期中的一等事实。

系统应遵循：

```text
先保留现场
→ 区分已验证、未验证和未知
→ 禁止用猜测替代事实
→ 给出可理解的下一步
→ 由用户决定 inspect / retry / skip / resume / cleanup
```

特别是：

- 未闭合的 lease 不应自动重跑；
- 没有 Receipt 的副作用应标记为 `unknown`；
- 失败的 worktree 默认保留；
- retry 应创建新 attempt，而不是覆盖旧现场；
- 已验证的进度不能因为 Provider 失败而丢失；
- cleanup、merge 和 release 需要独立的确认与证据。

恢复界面的目标不是向用户展示更多错误，而是让用户知道：

```text
已经发生了什么
哪些内容可以信任
哪些内容仍然未知
下一步有哪些安全选项
```

## 10. 自动化与用户主权

用户主权不等于所有操作都要求人工点击，自动化也不等于系统可以代替用户作出所有决定。

推荐使用风险自适应的确认策略：

| 操作类型 | 默认策略 |
|---|---|
| 低风险、局部、可逆操作 | 自动执行 |
| 隔离 worktree 内的代码施工 | 一次计划确认后执行 |
| 跨模块、跨任务或预算变化 | 展示影响并请求确认 |
| 合并、发布、删除、外部写入 | 明确的用户确认 |
| 副作用状态未知 | 暂停并进入恢复 |
| 计划或目标发生实质变化 | 新建 revision，不静默覆盖 |

系统约束的是隐式后果，不是用户表达合法目标和作出最终决定的权力。

### 10.1 契约驱动的安全分层

安全等级不应主要由项目名称、节点数量或预先选择的固定流程决定，而应由每次 Task / Run 的 Boundary Contract 推导。项目可以提供默认策略，但最终判断要结合：

- 上下文、文件、符号和 Artifact 范围；
- 可读、可写、可执行和可委派能力；
- 外部副作用、凭据、用户数据和不可逆操作；
- 任务依赖、Worker 数量、预计时长和预算；
- 验收要求、失败处理和恢复难度。

用户界面可以把契约表现为勾选项，系统内部必须保存为可验证结构：

```text
context
scope
capabilities
actions
artifacts
acceptance
budget
recovery
delegation
```

模板只是 Boundary Contract 的默认勾选集合，不应规定唯一的任务流程。上级向下级派发任务时，子契约只能收窄父契约；如果下级需要未授权能力，应产生 Capability Request 并暂停等待控制面决定。

安全评估可以从契约推导最低控制集合：小范围、可逆、无外部副作用的任务减少用户仪式，但仍保留基础事实和验收；跨模块、长时间、多 Worker 或高影响任务自动启用更完整的计划版本、lease、Evidence、Receipt 和 recovery。执行中发现边界扩大时只能升级，不能静默降级。

## 11. 产品设计不变量

以下不变量应成为设计、实现和验收时的共同检查表：

1. Agent 可以提出建议，但不能以文本宣布事实成立；
2. 用户可以决定方向，但模糊表达不能直接触发不可逆副作用；
3. 每个成员只获得完成职责所需的上下文和权限；
4. Agent 之间默认通过结构化项目事实交流；
5. 每个重要状态迁移都有来源、版本和可审计记录；
6. 每个成功结果都有宿主 Evidence；
7. 每个外部副作用都有 Receipt，或明确处于 `unknown`；
8. 失败现场默认保留，恢复动作不能静默发生；
9. 视图可以不同，但必须投影同一组项目事实；
10. 用户随时可以溯源，但不必默认承担全部内部复杂度；
11. 无法证明安全时暂停，而不是用模型猜测继续执行；
12. 第三方 Agent Runtime 可以替换，但不能取代项目事实源。

## 12. 不应该成为什么

SlimeMold 不应该变成：

- 让用户不断审批细节的官僚系统；
- 把所有项目内容都塞给每个 Agent 的上下文转发器；
- 以 Agent 人格和群聊为中心的多 Agent 展示产品；
- 把高级 DAG 当作所有用户默认入口的节点编辑器；
- 以模型自报成功替代真实验收的自动化脚本；
- 用更多节点、模板、连接器掩盖核心闭环没有成立的问题；
- 另一个不可解释的 Agent 来管理其他 Agent。

## 13. 产品判断标准

每增加一个功能，都应至少回答：

1. 它减少了哪一种用户或 Agent 的局部误判？
2. 它明确了谁可以知道、决定或执行什么吗？
3. 它是否增加了项目事实的可追溯性？
4. 它是否让失败更容易保留和恢复？
5. 它是否让用户更快理解下一步，而不是增加内部术语？
6. 它是否必须成为 SlimeMold 的核心能力，还是可以由 Provider、Runtime 或外部工具承担？
7. 它是否让“项目目标 → 计划 → 执行 → 证据 → 交付”这条闭环更可靠？

如果一个功能只能增加 Agent 数量、节点数量或视觉复杂度，却不能改善上述问题，就不应因为“看起来更智能”而进入近期主线。

## 14. 产品哲学宣言

```text
Agent 可以聪明，但不能天然拥有权威。

用户拥有决定权，但不能让模糊意图直接产生不可逆事实。

系统负责编译上下文、编排权限、维护状态、验证结果和保留溯源。

每个成员只获得完成职责所需的信息和能力。

高级工作台负责解释系统，而不是成为系统唯一的真实来源。

失败应当被保留、解释和恢复，而不是被隐藏或猜测成成功。

真正的交付不是 Agent 说完成了，而是项目能够证明、理解并继续前进。
```
