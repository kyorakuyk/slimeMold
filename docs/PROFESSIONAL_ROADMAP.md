# Professional 路线规划

面向进阶 / 专业用户的能力储备。这里记录的是「已确认要做、但当前版本刻意不做」的事项，
以及为什么现在不做、什么条件下开始做、怎么做。

Community（当前主线）追求的是「普通用户 5 分钟能跑通一条流水线」，
Professional 追求的是「复杂工程可维护、可协作、可版本化」。

---

## C. 真嵌套子图（Nested Subgraph）

### 现状：我们做了什么

当前版本走的是 **方案 A：子图引用 + 执行期扁平化**（已实现）：

- 子图定义存在项目级 `subgraphs` 字典里，本质是一份 `nodes/edges` 快照
- 画布上用 `subgraph.ref` 节点引用它，端口由 `resolvePorts()` 从子图定义动态解析
- 运行前 `flattenSubgraphs()` 把 ref 节点就地展开成内部节点（id 加 `refId::` 前缀），
  执行引擎看到的永远是一张扁平图 —— 拓扑排序、缓存、分支剪枝、增量运行全部零改动

同时实现了 **方案 B：节点组**（纯视觉编组，`groups` 字段），
解决「画布太乱」这一类纯视觉诉求，不参与执行。

A 和 B 是正交的：A 管复用与抽象，B 管整理与可读性。

### C 是什么

真嵌套子图 = 把子图当作一等公民的「工作流内嵌工作流」：

- 画布支持 **下钻编辑**（双击子图节点进入内部画布，面包屑导航返回）
- 子图有 **显式的 Input / Output 节点**（而非从未连接端口自动推断）
- 执行引擎 **原生理解层级**，不做扁平化，直接递归执行
- 子图有 **独立的作用域**：局部变量、局部 Agent 配置、局部资产命名空间
- 支持 **子图版本化**：引用时可锁定版本，子图更新不会静默破坏已有工作流

### 为什么现在不做

| 维度 | 说明 |
|---|---|
| 复杂度 | 执行引擎要从「一张图」改成「图的树」，缓存 key、状态回写、日志归属、错误堆栈全部要带上层级路径 |
| 收益比 | 方案 A 已经覆盖了 80% 的复用诉求，且对普通用户零学习成本 |
| UI 成本 | 下钻编辑需要面包屑、画布栈、跨层级复制粘贴、跨层级撤销重做，是一整套交互体系 |
| 风险 | 一旦引入层级，序列化格式变更不可逆，需要迁移脚本；现在改还很便宜，等用户量上来就贵了 |

### 何时开始做

满足以下任一条件时启动：

1. 用户反馈「子图套子图」的场景频繁出现（A 方案虽然支持递归展开，但没有下钻编辑体验很差）
2. 单个工作流节点数经常超过 60，扁平化后的执行图规模影响可观测性
3. 需要做「子图市场 / 团队共享库」，这时版本化与作用域隔离成为硬需求

### 怎么做（实施要点）

**第一步：显式 IO 节点，替换自动推断**

```
subgraph.input   —— 子图内部的入口，对外暴露为 ref 节点的一个输入端口
subgraph.output  —— 子图内部的出口，对外暴露为 ref 节点的一个输出端口
```

好处：端口顺序、命名、类型由用户显式控制，不会因为内部连线变化而端口漂移。
迁移：为现存子图自动生成 IO 节点（用当前 `inputs/outputs` 的 `innerNodeId/innerHandle` 反推）。

**第二步：画布下钻**

- `viewStore` 增加 `canvasStack: Array<{ kind: 'workflow' | 'subgraph', id: string }>`
- 顶部渲染面包屑：`主流程 / 图片预处理 / 缩放`
- 进入子图时，`WorkflowEditor` 的数据源从 `store.nodes` 切到 `store.subgraphs[id].nodes`
- 编辑即时写回子图定义，所有引用该子图的 ref 节点同步失效重算

**第三步：引擎原生层级执行**

- `runWorkflow` 递归：遇到 ref 节点，为其构造子 `ExecContext`（继承 agents、隔离 variables）
- 节点 id 用路径表示：`main/sg1/node3`，日志、状态、错误堆栈都带完整路径
- 缓存 key 加入层级路径，避免不同实例互相污染
- 保留扁平化作为 **调试视图**（「展开查看实际执行图」），而非执行手段

**第四步：作用域与版本**

- 子图内部 `variables` 默认隔离，通过显式的 `scope: 'inherit' | 'isolated'` 控制
- `SubgraphDef` 增加 `version: string`，ref 节点记录 `lockedVersion`
- 子图更新时提示「N 处引用受影响」，支持批量升级 / 保持旧版

## D. 多项目同开 + 标签页分组

### 背景

「项目」概念的 Community 一期（见 `TODO.md` 第五节）确立了：项目文件夹形态、磁盘为唯一真相、
资产/变量两级、手动保存 + dirty 标记、恢复上次打开的界面。

以下两项在讨论中已确认要做，但**刻意推迟到 Professional**。

### D1. 多项目同开

**目标**：标签栏可同时打开多个项目，各项目独立运行、互不干扰。

**Community 一期的约束**：同一时刻**只允许一个工作流在跑**（单项目、单运行）。

**Professional 目标态**：
- 允许**多个工作流甚至多个项目同时运行**
- 运行状态、日志、成本账本、节点缓存**按项目隔离**

**为什么现在不做**：

| 维度 | 说明 |
|---|---|
| 状态隔离 | 当前 `workflowStore` 是单例全局 store，`running`/`logs`/`runHistory`/`nodeCache` 全是单份，多项目并行需要拆成「按项目分片」的状态树 |
| 执行引擎 | `runWorkflow` 依赖 `useWorkflowStore.getState()` 读写激活工作流，并行运行需把执行上下文与 store 解耦，改动面大 |
| 并发资源 | 多项目同跑会放大 API 限流、本地算力争抢问题，需要全局并发闸门与配额策略 |
| 收益比 | 单人创作场景下，先把单项目体验做扎实收益更高 |

**何时开始做**：单项目体验稳定，且出现「跑长任务时想同时编辑另一个项目」的真实诉求时。

**怎么做（要点）**：
- `workflowStore` 按 `projectId` 分片：`projects: Record<string, ProjectState>`，全局只留 UI 偏好与 agents
- 执行引擎接收显式的 `ProjectState` 句柄而非从全局 store 取，`nodeCache` 的 key 加项目前缀
- 增加全局并发闸门（最大并行运行数、按 provider 的限流配额）
- 状态栏/标签页展示各项目运行态，避免用户搞不清"到底谁在跑"

### D2. 标签页分组（Chrome / Edge 风格）

**目标**：工作流标签支持**分组、着色、折叠/展开、拖拽排序**，分组状态存 `project.json`。

**Community 一期的约束**：`workflows` 是无序字典，标签平铺，无分组无排序。

**为什么现在不做**：
- 依赖 D1 的多项目标签栏一起设计，否则做两遍
- 需要给 `ProjectFile` 增加 `tabGroups` 与工作流 `order` 字段，序列化格式变更宜与 D1 一次性做完
- 拖拽排序 + 折叠动画 + 跨组拖拽是一整套交互，成本不低

**怎么做（要点）**：
- `ProjectFile` 增加 `tabGroups: Array<{ id, name, color, collapsed, workflowIds }>` 与工作流 `order`
- 标签栏支持组内/跨组拖拽、右键分组菜单、组标题双击重命名
- 折叠状态属会话状态（localStorage），分组结构属项目数据（`project.json`）—— 两者分开存

## 其他 Professional 储备项

以下条目同样归入 professional，暂不排期，按需提级：

- **执行队列**：多次运行排队、优先级、批量参数扫描（ComfyUI 的 queue prompt）
- **断点与单步调试**：在节点上打断点，逐节点执行并检视中间产物
- **子图市场**：导入/导出子图为独立文件，团队间共享
- **协作与版本**：工作流 diff、冲突合并、变更历史
- **自定义节点 SDK**：正式的插件 API 与类型声明包，而非当前的目录扫描
- **远程执行后端**：把执行下沉到服务端，前端只做编排与结果回显
